Events

An event marks a stimulus, behavioral condition, or other interval that can be aligned with imaging frames. Continuous .dat recordings use Save Folder events.mat; event-split UMT data carries its own top-level eventInfo.

Detection, conditions, and repetitions

  1. Events Manager reads analog signals and uses threshold, polarity, trigger type, minimum inter-stimulus interval, and optional filtering to identify event intervals.
  2. A condition list assigns IDs/names in chronological order.
  3. Repeated event IDs become repetitions of the same condition.
  4. The baseline duration and acquisition frame rate convert each event interval into a frame selection.

Validation

The EventsManager object normalizes saved fields, checks compatible lengths and IDs, verifies timing against acquisition information, and rejects selections that cannot produce usable frame matrices. A missing file disables event features; malformed metadata is not guessed from imaging intensity.

How DataViewer uses events

Normal mode draws event intervals over the continuous trace. Event mode selects a condition and repetition, builds an event-relative frame matrix, and can average repetitions. Deleting and restoring conditions in the viewer changes normalized in-memory selection; Events Manager owns saved edits.

Analysis and event-split data

Functions such as split_data_by_event and genAmplitudeMaps use event timing to create or aggregate event-aligned data. A UMT event axis is described by eventID, repetitionIndex, eventName, and eventAxisMode; it remains interpretable after the UMT file leaves the Save Folder.

Recovery

Condition-name editing keeps an original list that Restore can recover before saving. Closing Events Manager with unsaved changes asks for confirmation. Replace an existing events.mat only through the tool or validated code, and keep backups for irreplaceable event annotations.
